# Nosh Client

React front end for Nosh, a meal planning platform. The ASP.NET API lives in `../Server`.
Voice: warm and practical. Never preachy or judgemental about budgets. Plain language, short words, no jargon, no guilt.

## Stack

- **Bun** runtime, package manager and bundler (`bun-plugin-tailwind`). No Vite, no Node tooling.
- **React 19** + TypeScript (strict).
- **TanStack Router** with code-based routes (Bun has no file-route plugin) and **TanStack Query** for server state.
- **Tailwind CSS v4** (config lives in CSS, no `tailwind.config`) and **shadcn/ui** (style `new-york`, `components.json`).
- Dev/prod server is `src/index.ts`: serves the SPA and proxies `/api/*` to the API (`API_URL`, default `https://localhost:7263`, the API's local HTTPS address; its self-signed development certificate is accepted outside production). Fetch with relative `/api/...` URLs.

## Commands

```bash
bun install
bun dev          # dev server with HMR on :3000
bun run typecheck
bun run build    # static build to dist/
bun start        # production server
```

Docker: `docker compose up --build` here (client only) or from the repo root (client + API).

## Architecture

The app is **feature-driven**. Each core feature (recipes, ingredients, calendar, ...) owns a folder under `src/features/` and holds everything it needs. Code shared by more than one feature lives outside `features/`.

```
src/
  index.ts / index.html / frontend.tsx   server, HTML shell, React entry (router + query providers)
  routes/__root.tsx                      root route: composes the app shell (left nav and the page)
  routeTree.ts                           composes the route tree from each feature's routes
  features/
    <feature>/
      api/
        <controller>.queries.ts          ALL API calls for one backend controller (see below)
      hooks/
        use<Thing>.ts                    one hook per file, wraps the queries file
      components/                        components used only by this feature
      pages/                             route components for this feature
      routes.ts                          this feature's routes (createRoute), exported to routeTree.ts
      types.ts                           feature types (API DTOs, view models)
      index.ts                           public surface: what other code may import from this feature
  components/                            shared app components (Logo.tsx)
  components/layout/                     app shell: AppLayout (3 columns, stacks on small screens), SideNav
  components/ui/                         shadcn primitives, add with the shadcn CLI
  lib/
    utils.ts                             cn() helper
    api/
      client.ts                          API client setup: base URL, auth, interceptors, error handling
      generated/                         generated API client and types (never hand-edit)
      index.ts                           public surface of lib/api
  assets/                                logos and images
styles/globals.css                       theme: brand palette + semantic tokens
```

Import with the `@/` alias (`@/features/meals`, `@/components/...`).

### Feature rules

1. **One folder per feature.** New functionality goes into the feature it belongs to, or a new feature folder. Don't add feature code to `src/components/`.
2. **Features don't reach into each other.** Import another feature only through its `index.ts`. If two features need the same thing, move it to `src/components/` or `src/lib/`.
3. **Shared code never imports from a feature.** `components/`, `lib/` and `components/ui/` stay feature-agnostic.
4. **Routes belong to features.** Each feature exports its routes from `routes.ts`; `routeTree.ts` only composes them. Route components live in the feature's `pages/` and stay thin: they compose hooks and components.
5. **Keep it flat until it hurts.** Don't create `hooks/` or `components/` subfolders for a single file you could keep beside its user; split when a folder gets crowded.

### API rules

Server access has four layers. Each layer only talks to the one below it.

1. **`lib/api`: generated client and client setup.** `src/lib/api/generated/` holds the typed SDK and types generated by `@hey-api/openapi-ts` from the server's OpenAPI document (`openapi-ts.config.ts`). It is output only: never hand-edit it, and commit it. Regenerate after any controller change: start the server (`dotnet run` in `../Server/NoshServer.Api`), then `bun run generate:api` (`OPENAPI_URL` overrides the source; the script turns off TLS verification because the server uses the self-signed development certificate). Only the SDK and types are generated; the TanStack Query plugin is deliberately not used, because the queries files own keys and `queryOptions`. `src/lib/api/client.ts` is where the client is configured: base URL, auth (tokens/headers), interceptors and global error handling. The client is configured with `throwOnError: true`, so SDK calls throw on non-2xx. Nothing feature-specific goes here.
2. **Queries file: one per backend controller, the bank of requests.** `features/<feature>/api/<controller>.queries.ts` (for example `meals.queries.ts` for `MealsController`) is the only place in the feature that calls the generated client. It contains, for that controller only:
   - every request for the controller (`getMeals`, `getMeal`, `createMeal`, ...), as thin functions over the generated client,
   - the query key factory (`mealKeys.all`, `mealKeys.detail(id)`),
   - `queryOptions(...)` for each read, so keys, functions and caching are defined once.
   A feature only gets an `api/` folder if it talks to the API.
3. **Hooks: one per file.** `features/<feature>/hooks/useMeals.ts`, `useMeal.ts`, `useCreateMeal.ts`, ... Each hook calls the queries file (via its `queryOptions` or request function) and wraps it in `useQuery` / `useMutation`, including cache invalidation through the key factory. Name reads `use<Thing>` and writes `use<Verb><Thing>`.
4. **Components and pages (including anything built on `components/ui`) use hooks only.** They import from `hooks/` (or the feature's `index.ts`) and never from `*.queries.ts`. They don't build query keys or call the generated client. Importing the generated **types** (`import type { ... } from "@/lib/api/generated"`) is fine.

Also:
- Request/response types come from the generated SDK. Feature `types.ts` is for view models and UI-only types, not copies of DTOs.
- Route loaders may call `queryClient.ensureQueryData(<queryOptions>)` using the `queryOptions` exported from the queries file; that is the one allowed use outside a hook.
- Mutations invalidate through the key factory, never by hand-written key arrays.
- Errors: the SDK throws on non-2xx; handle them via the query's `error` state in the component, not with try/catch in the hook.

Example shape:

```ts
// features/meals/api/meals.queries.ts
import { getMeals as sdkGetMeals } from "@/lib/api/generated";

export const mealKeys = { all: ["meals"] as const, detail: (id: string) => ["meals", id] as const };
export const getMeals = async () => (await sdkGetMeals()).data;
export const mealsQuery = () => queryOptions({ queryKey: mealKeys.all, queryFn: getMeals });

// features/meals/hooks/useMeals.ts
export const useMeals = () => useQuery(mealsQuery());

// features/meals/pages/MealsPage.tsx
const { data, isPending } = useMeals();
```

(`getMeals` is illustrative: SDK function names come from the controller's operation ids.)

## Current features and layout

- **App shell:** `routes/__root.tsx` composes `AppLayout` with `SideNav` (left) and the page. Below `lg` the nav is a sticky top bar with the logo centred and a three-lines button; opening it takes over the whole screen with the links and the Preferences button (the page behind stops scrolling, Escape or picking a link closes it). From `lg` up it is the always-open left sidebar.
- **`schedules` (the home page, `/`):** a weekly calendar and the focus of daily use. `?week=YYYY-MM-DD` shows the week containing that date (weeks start on Monday); no param means the current week. It reads `GET /schedules?From=&To=` through `useScheduleOccurrences`. The calendar is `WeekCalendar`, which shows a **grid** (`WeekGrid`: a table with a column per day and a row per meal, Breakfast to Dessert, recipes as chips in the cells, today's column highlighted) when its container is at least `@2xl` wide, and a stacked **list** of days (`WeekList`) otherwise. It switches on the width of its own container (Tailwind `@container` queries), not the screen, because the left nav takes part of the screen. Recurring schedules show a repeat icon. Grouping helpers and the meal row order live in `features/schedules/calendar.ts`.
- **Calendar cards:** every occurrence is an `OccurrenceCard` (used by both `WeekGrid` and `WeekList`). Its left stripe and tag show stock: Ready (green), Some missing (leaf), Missing (coral), from the server's `availability`. Each state has an icon and a label, never colour alone. Completed and skipped meals have no availability, so they show a muted card with a Done or Skipped tag instead. The check button completes the meal (`POST /schedule-events`, which takes the ingredients out of stock on the server) and Undo deletes the event (stock is not put back). Clicking the name opens `OccurrenceDialogContent`: the recipe, each ingredient's stock state, `StockQuickAdd` for lacking ingredients, and Complete, Skip or Undo. The header shows a `WeekProgress` tag ("3 of 8 done", skipped meals left out of the total).
- **Planning a recipe:** `ScheduleDialog` (a trigger plus `ScheduleForm`) creates a schedule with `POST /schedules`. It has three entry points. An empty calendar cell (grid) or day (list) opens it prefilled with that date, the meal (grid only) and "Just once"; the header's "Plan a recipe" button opens it with today's date and nothing else chosen, so the user decides how often it repeats. The form takes a recipe (`RecipeCombobox`, which by default only offers recipes matching the saved dietary preference, with a switch to show all), a date, a meal, and how often (just once, daily, weekly on chosen days, monthly, with an interval and an end of never, on a date or after N times). Saving refreshes the calendar, shopping list and availability, and moves the calendar to the week of the start date.
- **Stock-dependent queries refresh together:** stock, availability and the shopping list all depend on each other, so every mutation that changes stock or events calls `invalidateStockDependents` (`lib/queryKeys.ts`). The query-key roots live there (`queryRoots`) and each feature's key factory builds on them, which is how features invalidate each other's data without importing one another.
- **`inventory` (`/inventory`, last in the side nav):** a searchable, paged table of stock with inline edit (`PUT`, sets the quantity), "Used up" (`DELETE`) and an "Add stock" dialog (`POST`, which adds to what is already in stock). `QuantityFields` is the amount and unit input used by all of them. The feature's `index.ts` exports `StockQuickAdd` and `useAddStock` for the calendar dialog and the shopping list. Quantities are displayed with `formatQuantity` (`lib/quantity.ts`); the API sends decimals as numbers or strings, so convert with `toNumber`.
- **`shopping-list` (`/shopping-list`):** reads `GET /shopping-list?From=&To=` for the week. Sections: To buy, Covered, and In stock but not planned. Ticking a To buy row adds the shortfall to stock (`useAddStock`), and the row moves to Covered after the refetch; there is no local checked state, and un-ticking is done on the Inventory page. A row with a unit mismatch can't be ticked and links to the Inventory page.
- **`preferences` (dietary preferences, no page of its own):** the API allows any number of preference rows, so **this client keeps it to one**: it always reads the oldest (`GET /preferences?PageSize=1`) and updates it, creating one only when none exists (`savePreference`). `PreferencesGate` (mounted in the root route) opens a modal that cannot be dismissed whenever there is no preference, so it is always the first thing a new instance sees; saving it takes the user to `/recipes`. Afterwards the nav's `Preferences` button (passed to `SideNav` as `footer`, since shared components can't import a feature) edits it. `useSavePreference` takes its `onSaved` callback as a hook argument because saving closes the dialog and unmounts the form that called `mutate`. Other features read the value through `usePreference`.
- **Recipe dialog:** clicking a recipe name in My recipes opens `RecipeDialog`, a tabbed dialog (`components/Tabs.tsx`, a small accessible tablist; Radix tabs aren't installed). **Details** shows ingredients and method (`RecipeDetails`, shared with the starter dialog). **Schedules** is `RecipeSchedulesPanel` from the schedules feature: every schedule for that recipe (`GET /recipes/{id}/schedules`, ended ones included) with Change, Delete (with a confirm step) and "Plan this recipe". Changing or creating reuses `ScheduleForm`, which takes `schedule` (edit) and `recipe` (fixes the recipe, no picker) and, with `onCancel`, renders inline inside the dialog instead of as its own. Clicking a starter recipe's name opens `SampleRecipeDialog` (details and Add to my recipes; there is no Schedules tab as it is not a recipe yet). `recipes` and `schedules` import each other through their `index.ts` (the dialog needs the panel, and planning needs the recipe picker), so keep anything evaluated at module load out of those imports.
- **Dietary filter on recipes:** both lists (My recipes and Starter recipes) start filtered by the saved dietary preference and share the `DietaryFilter` tags at the top. `useDietaryFilter` reads the URL `dietary` param: absent means "not chosen yet" so the preference applies, an empty list means the user chose All, and any other list is their own pick. The choice is kept when switching between the two lists. "Your recipe book is empty" is decided from an unfiltered count, so a filter that matches nothing never hides the starter list from a user with no recipes.
- **`recipes` starter recipes:** `?view=starter` shows `StarterRecipes`: the built-in samples (`GET /recipes/samples`), starting filtered by the saved dietary preference, each with "Add to my recipes". A sample has ingredient names rather than ids, so `useImportSampleRecipe` finds or creates each ingredient (`ensureIngredient` from the ingredients feature, matching names ignoring case) and then creates the recipe. `MyRecipes` shows the starter list under an "empty recipe book" message when the user has no recipes at all, so a blank slate always has a way forward.
- **`recipes` (`/recipes`) and `ingredients` (`/ingredients`):** the same page shape: a heading, a search box, (recipes only) dietary filter tabs, a table and a pagination bar. State lives in the URL (`?q=`, `?page=`, `?dietary=`), so back/forward and refresh keep the view. They read `GET /recipes` and `GET /ingredients`, 20 rows per page. Recipes can be filtered by name and dietary requirement (all selected requirements must match). Filtering recipes by meal type needs a server parameter that doesn't exist yet, so there is no meal type filter.
- **Create dialogs:** the recipes and ingredients pages have a "New ..." button that opens a dialog (`CreateRecipeDialog`, `CreateIngredientDialog`). The form lives in a child component rendered inside the dialog content, so its state resets every time the dialog closes. Forms use plain React state and a mutation hook (`useCreateRecipe`, `useCreateIngredient`) that invalidates that feature's list queries on success; server validation errors are shown with `ErrorList` (`lib/problem.ts` turns an API problem response into messages). The recipe form picks ingredients with `IngredientCombobox` (exported from the ingredients feature), which searches existing ingredients and can add a missing one on the spot.
- **Shared list pieces** (`components/`): `SearchInput` (debounced, writes the URL after 300ms), `FilterTabs` (an All button plus toggles, so several can be on at once; `showAll={false}` makes it a plain multi-select, used in the recipe form), `Pagination`, `ErrorList`. Use them for any new list page. Enum value lists and display labels (`MEAL_TYPES`, `DIETARY_REQUIREMENTS`, `CUISINES`, `RECIPE_TAGS`, `MEASUREMENT_UNITS`, `humanize`) are in `lib/enums.ts`; URL search parameter parsers are in `lib/search.ts`.
- **Navigation:** `components/layout/SideNav.tsx` lists the pages; add a new page to its `items` array.
- **Dates:** the API uses calendar days as `YYYY-MM-DD`. Use the helpers in `lib/dates.ts` (local-day based, no UTC conversion) rather than `toISOString()`. Avoid very new built-ins (for example `Map.groupBy`) since the app has to work on older phones.

- Don't use the `bun-react-template` demo patterns (the `/api/hello` routes and so on); they have been removed.

### Use tokens, not hex

Use semantic Tailwind classes (`bg-primary`, `text-foreground`, `text-muted-foreground`, `border-border`) in components. Use brand classes (`bg-nosh-charcoal`, `text-cloud-grey`, `text-nosh-green`) only for deliberately branded surfaces such as the header. Never hard-code hex values, `text-white`, `text-black` or `bg-black` in components.

These lighter and tinted values are used through the semantic tokens in `globals.css`, not as their own classes: `#4EAE9A` is `secondary` (Deep Teal for fills that carry Charcoal text), `#F4845D` is `destructive` (Flame Coral for fills that carry Charcoal text), `#F2F6F4` is the light `background`, `#D8DCE0` is `border` (decorative edges only, see colour rule 10), `#7F8A91` (dark `#838E96`) is `input`, the control-edge colour at 3:1 or better on white, Mist and the cards, and `#1F7A68` (Teal Ink) is the light `ring` (dark `#62CC9B`), and `#4A555F` is `muted-foreground` on light and the dark `border`. Add a token to `@theme` only when something needs it as a class.

### Colour rules

1. **Charcoal is for backgrounds and text.** Body and heading text on light surfaces is Nosh Charcoal.
2. **Never use white or black for text or foreground.** On Charcoal surfaces, text is Cloud Grey. Nosh Green may be used for headings, links and emphasis on Charcoal. White is allowed only as a surface (cards) or inside the supplied logo.
3. **Nosh Green leads.** It is the primary colour. Teal and Charcoal support it. Flame Coral and Leaf are small accents (highlights, badges, warnings), never large fills or page backgrounds.
4. **Text on a brand colour is Charcoal**, never white. Green `6.1:1`, Leaf `6.8:1`, `secondary` (`#4EAE9A`) `4.5:1`, `destructive` (`#F4845D`) `4.8:1`.
5. **Don't put raw Deep Teal or Flame Coral behind small text** (Charcoal on them is `4.0:1` and `4.3:1`, below AA). Use the `secondary` / `destructive` tokens, or keep the raw colour for icons, borders, large bold text and decoration.
6. **Don't use Nosh Green, Teal or Coral as text on white or Mist** (all under 4.5:1). On light surfaces use Charcoal, or `teal-ink` for links.
7. **WCAG AA is the minimum**: 4.5:1 for normal text, 3:1 for large text and UI boundaries. It must work on older, small phones: keep tap targets at least 40px and body text at least 16px.
8. **Colour is never the only signal.** Pair coral/leaf states with an icon or text.
9. **Hover and focus states** use `hover:brightness-105` or a solid token (`hover:bg-accent`), never opacity or a transparent tint (`opacity-*`, `bg-accent/40`, `ring-ring/50`). Reducing opacity over a background lowers contrast with Charcoal text. Disabled and loading states may dim, but anything that must stay readable still needs its contrast while dimmed (lists dim to `opacity-90` while refetching because muted text drops below 4.5:1 at `opacity-80` and under).
10. **Control edges need 3:1.** The border of an input, select or outlined button, and any edge a person needs to find a control by, must be at least 3:1 against the surface it sits on (WCAG 1.4.11). Use the `input` token for these, and keep `border` for decoration (cards, dividers). Check this in the light and the dark theme.
11. **Affordances keep full contrast.** An icon or outline that tells people they can act (the + in an empty calendar cell, a drag handle, a chevron) is a meaningful icon, so it needs 3:1 and is never faded to look quiet.

### Clickable things show a pointer

Tailwind v4's reset gives buttons the default arrow cursor, so `styles/globals.css` has a base rule that restores `cursor: pointer` for enabled buttons, `role="button"`, `role="tab"`, `role="option"`, `summary`, labels with `for` and checkboxes or radios. Links already have it. Any other element that handles a click (a table row, a card, a `div`) needs `cursor-pointer` on it, and Radix list items (for example `SelectItem`) must not use `cursor-default`. A clickable row or card keeps a real button inside it for keyboard users, and any button inside it that does something else calls `stopPropagation()`.

### Accessibility and small phones

Nosh serves people on older, smaller phones, so **WCAG 2.1 AA is the minimum, not a goal**. Check every new screen and component against these before calling it done:

1. **Contrast.** 4.5:1 for normal text, 3:1 for large text (24px, or 18.66px bold) and for icons and borders that carry meaning. Use the palette and the pairings in the colour rules above. If you need a pairing that isn't already used somewhere, work out its ratio first, and check it in both the light and dark themes.
2. **Colour is never the only signal.** Pair it with an icon or text (the calendar's stock tags say Ready, Some missing or Missing as well as being green, yellow or coral).
3. **Tap targets are at least 40px by 40px**, with a little space between them. A default `Button` is 40px tall, `size="icon"` and `size="icon-lg"` are 40px square (icon-only buttons always need an `aria-label`), and nav links use `min-h-11` or more. The `sm` and `icon-sm` sizes are under 40px, so don't use them for actions on touch. Inputs and select triggers are `h-10`.
4. **Text is at least 16px, everywhere.** That includes captions, tags, table headers, form labels, error text and the text inside buttons and badges. **Don't use `text-sm`, `text-xs` or an arbitrary size below 16px** (for example `text-[11px]`); use `text-base` or larger. Tell secondary text apart by colour (`text-muted-foreground`) and weight, not by making it smaller. Allow short labels to wrap rather than shrink them.
5. **Layout.** Design the phone first and widen up: it must work at 320px and 375px wide with no sideways scrolling of the page (a table may scroll inside its own container). Dialogs must fit the screen and scroll inside themselves (`max-h-[90dvh]`).
6. **Nothing is hover-only.** Hover can add polish but everything must work by tap and by keyboard.
7. **Keyboard and screen readers.** Use real buttons and links, keep the visible focus ring (`focus-visible:ring-[3px] focus-visible:ring-ring`, as the `ui/` components do; it is solid and at least 3:1, and on the Charcoal nav it is `ring-nosh-green`), label every input (`aria-label` when there's no visible label), and use `aria-pressed`, `aria-selected` and `aria-current` for toggles, tabs and the current page. Errors that appear after an action use `role="alert"`. Use the Radix dialog so focus is trapped and Escape closes it.
8. **Older browsers.** Avoid very new JavaScript built-ins (for example `Map.groupBy` or `toSorted`) and check a new CSS feature on caniuse before using it. The calendar already relies on container queries, which need a reasonably recent browser, so don't add more of that kind without a reason.
9. **Keep it light.** No heavy dependencies or large images. Look at the size `bun run build` reports before and after adding a library.
10. **Words.** Plain, short, warm. No jargon and no guilt.

To check UI work: run `bun run typecheck` and `bun run build`, view the page at 320px and 375px wide (the browser pane's Mobile preset), tab through it with the keyboard, and look at it in the dark theme.

### Voice

Warm and practical, like a friend who is good with money and never makes you feel bad about it.

- **Plain words, short sentences.** "We couldn't load your recipes. Please try again." not "Request failed (500)".
- **Never judge a budget or a choice.** No "only", "just", "simply", "you should have" or "unfortunately". Don't comment on what people can or can't afford.
- **No jargon.** No "mismatch", "invalid", "entity" or error codes in what people see. Say what happened and what to do next.
- **No guilt.** Missing stock, a skipped meal or an empty week are normal states, not mistakes: "Some missing", "Skipped", "Nothing planned".
- **Say what will happen.** Buttons say the action ("Add to my recipes", "Plan it"), and the first thing a new person sees should always have a way forward.

### Adding shadcn components

`bunx --bun shadcn@latest add <component>`, then check the result against the rules above. Generated components may contain `text-white`, opacity-based hovers or focus rings (`/50`), `text-sm` or `text-xs`, 36px (`h-9`) controls, or a faint `border` on inputs and outlined buttons: replace them with the tokens, `text-base` and the 40px sizes.
